ห้องนิรภัยบัญชี PROTOTYPE · ข้อมูลสมมติ

นี่คือ prototype — ข้อมูลทั้งหมดเป็นของสมมติและเก็บในเบราว์เซอร์นี้เท่านั้น ห้ามใส่รหัสจริง · การเข้ารหัสเป็นของจริง (AES-256-GCM + PBKDF2) ลองกด “ข้อมูลที่เซิร์ฟเวอร์เห็น” เพื่อดูว่าฐานข้อมูลจะเก็บอะไร · ล็อกอัตโนมัติเมื่อไม่ใช้งาน 5 นาที

แผน: ระบบจัดการบัญชีและรหัสผ่าน

ปัญหาตอนนี้ — รหัสผ่านกระจายอยู่ในคลังความรู้ 14 เรื่อง (ส่วนใหญ่ Odoo) และในงานอีก 3 งาน ทุกคนในทีมอ่านได้ ไม่รู้ว่าใครเห็นเมื่อไหร่ ไม่มีกำหนดเปลี่ยนรหัส และรหัสเดิมยังอยู่ใน backup ทุกชุด

เป้าหมาย

  • ปลอดภัย: ฐานข้อมูล, backup, ผู้ดูแล Supabase และใครที่ได้ service key ไปต้องอ่านรหัสไม่ได้
  • มีประสิทธิภาพ: หา account ได้ใน 2 วินาที, คัดลอกรหัสโดยไม่ต้องให้รหัสโผล่บนจอ, รู้ว่ารหัสไหนถึงเวลาเปลี่ยน
  • ตรวจสอบได้: ใครดู / คัดลอก / แก้ / เปลี่ยนรหัส เมื่อไหร่ — บันทึกแบบเพิ่มได้อย่างเดียว (แบบเดียวกับทะเบียน API)
  • เชื่อมกับงาน: ทะเบียน API ช่อง Auth และคลังความรู้อ้างถึงบัญชีได้โดยไม่ต้องใส่รหัส

ทางเลือก

A. Password manager สำเร็จรูป
(Bitwarden / 1Password / Vaultwarden)		B. ห้องนิรภัยใน Job Schedule
(เข้ารหัสฝั่งเบราว์เซอร์)		C. เก็บใน Supabase ธรรมดา + RLS
ความปลอดภัยสูงสุด — ผ่านการตรวจสอบ, 2FA, แยกสิทธิ์รายคนดี — server เห็นแต่ข้อมูลเข้ารหัส แต่เราดูแลโค้ดเข้ารหัสเองไม่พอ — ผู้ดูแล DB, service key, backup อ่านรหัสได้
ถอนสิทธิ์คนออกง่าย รายคนต้องเปลี่ยน passphrase (ระยะที่ 3 แก้ด้วย key รายคน)ลบ user
ค่าใช้จ่ายมีแผนฟรี/เสียเงินรายคน (ตรวจราคาล่าสุด)ฟรีฟรี
เชื่อมกับงาน / APIผ่านลิงก์ไปยังรายการในตัวในตัว

คำแนะนำ: A + ทะเบียนบัญชีในแอป — ใช้ password manager เก็บรหัสจริงของระบบ LIVE และบัญชีสำคัญ ส่วน Job Schedule มี “ทะเบียนบัญชี” เก็บข้อมูลที่ไม่ใช่ความลับ (ระบบ, environment, username, URL, ผู้ดูแล, วันเปลี่ยนรหัสล่าสุด) + ลิงก์ไปยังรายการใน password manager · ถ้ายังไม่มี password manager ใช้ B เป็นทางชั่วคราวได้ (คือสิ่งที่ prototype นี้สาธิต) · ไม่ใช้ C

การออกแบบ (ตามที่ prototype สาธิต)

  • แยกข้อมูลสองชั้น: metadata อ่านได้ทั้งทีม (ค้น/กรองได้) · ตัวรหัสเป็น ciphertext เท่านั้น หรือเป็นลิงก์ไป password manager
  • เข้ารหัสในเบราว์เซอร์ (end-to-end): PBKDF2-SHA256 600,000 รอบ → คีย์ AES-256-GCM · IV สุ่มใหม่ทุกครั้งที่บันทึก · ผูก ciphertext กับ id ของบัญชี (AAD) จึงสลับรหัสข้ามบัญชีไม่ได้ · ตรวจ passphrase ด้วย verifier ไม่เก็บ passphrase ที่ไหนเลย
  • ใช้งานปลอดภัยโดยไม่ต้องคิด: รหัสซ่อนเป็นค่าเริ่มต้น, เปิดดูแล้วซ่อนเองใน 20 วินาที, คัดลอกแล้วล้าง clipboard ใน 30 วินาที, ล็อกเองเมื่อไม่ใช้งาน 5 นาที, ตัวสร้างรหัสแบบสุ่มจริง (crypto)
  • กำหนดเปลี่ยนรหัส: LIVE ทุก 90 วัน, STD66 ทุก 180 วัน (ปรับได้รายบัญชี) — แสดงสถานะ “ใกล้ครบ / เกินกำหนด” และกรองได้
  • บันทึกการใช้งาน: ดูรหัส / คัดลอก / แก้ / เปลี่ยนรหัส ต่อบัญชี · ในระบบจริงบันทึกผ่านฟังก์ชันในฐานข้อมูล แก้หรือลบไม่ได้

ข้อจำกัดที่ต้องรู้ (ตรงไปตรงมา)

  • การเข้ารหัสในเบราว์เซอร์ป้องกัน server / backup / ผู้ดูแล DB ได้ แต่ไม่ป้องกันเครื่องผู้ใช้ที่ติดมัลแวร์ หรือคนในทีมที่รู้ passphrase แล้วตั้งใจนำรหัสออกไป
  • บันทึก “ดูรหัส” มาจากเบราว์เซอร์ — คนที่ถอดรหัสเองนอกแอปจะไม่ถูกบันทึก (password manager จริงก็มีข้อจำกัดคล้ายกันเมื่อแชร์รหัสไปแล้ว)
  • passphrase ร่วมของทีม: ใครออกจากทีม ต้องเปลี่ยน passphrase และเปลี่ยนรหัสระบบที่เขาเคยเห็น
  • ลืม passphrase = กู้รหัสคืนไม่ได้ (ตั้งใจให้เป็นอย่างนั้น) → เก็บ passphrase ไว้ในซองปิดผนึก / password manager ของหัวหน้า

โครงสร้างข้อมูล (ระบบจริง — schema v9; v8 ใช้กับแผนผังระบบแล้ว)

accounts      id, system, env (LIVE/STD66/อื่น ๆ), name, username, url, owner,
              secret_mode ('ref' | 'vault'), secret_ref (ลิงก์ password manager),
              secret_ct jsonb {iv, ct} — ciphertext เท่านั้น,
              rotate_days, rotated_at, job_nos[], api_ids[], note_ids[],
              created/updated by + at (trigger)
vault         1 แถว: kdf 'PBKDF2-SHA256', iterations, salt, verifier {iv, ct}
account_events  append-only: account_id, action (view/copy/edit/rotate), by, at
              — insert ผ่านฟังก์ชัน log_account_event() เท่านั้น, revoke update/delete
RLS: authenticated อ่าน/เขียน accounts ได้ (เพราะ secret เป็น ciphertext), anon ไม่ได้
backup: ได้แต่ ciphertext — กู้คืนแล้วต้องใช้ passphrase เดิม

แผนทำงาน

ระยะทำอะไรเวลา
0 · ทันทีย้ายรหัสจริงออกจากคลังความรู้ (ปุ่ม “ตรวจรหัสผ่าน” มีอยู่แล้ว) → แทนด้วย <password> · เปลี่ยนรหัสของระบบที่เคยถูกบันทึกไว้ (Odoo admin ฯลฯ) · ตัดสินใจเลือก password managerครึ่งวัน
1 · ทะเบียนบัญชีเมนู “ทะเบียนบัญชี” ในแอป: metadata + ลิงก์ password manager + กำหนดเปลี่ยนรหัส + บันทึกการใช้งาน · เชื่อมกับงานและทะเบียน API (ช่อง Auth เลือกบัญชีแทนการพิมพ์)1–2 วัน
2 · ห้องนิรภัย (ถ้าเลือก B)เข้ารหัสในเบราว์เซอร์ตาม prototype · หน้าตั้ง passphrase ครั้งแรก · ระบบตรวจรหัสผ่านในคลังความรู้มีปุ่ม “ย้ายเข้าห้องนิรภัย”2–3 วัน
3 · key รายคนแต่ละคนมีคู่กุญแจ (ECDH) ใช้ห่อคีย์ห้องนิรภัย → ถอนสิทธิ์รายคนได้โดยไม่ต้องเปลี่ยน passphrase ทั้งทีม3–5 วัน

ขั้นตอนปฏิบัติ (ใช้กับทุกทางเลือก)

  • คนเข้าใหม่: เพิ่ม user → ให้สิทธิ์เฉพาะบัญชีที่ใช้งาน
  • คนออก: ปิด user ทันที → เปลี่ยนรหัสทุกบัญชีที่เขาเคยดู/คัดลอก (ดูจากบันทึกการใช้งาน)
  • บัญชีระบบ: แยก user สำหรับคน กับ user สำหรับ API/service · ห้ามใช้ admin/sa ให้โปรแกรมเชื่อมต่อ
  • ห้าม: ส่งรหัสทาง LINE/อีเมล, ใส่รหัสในโค้ดหรือ git, แคปหน้าจอที่มีรหัส
